# ONNX: CPU и аппаратный NNAPI

`scripts/prepare-nnapi.sh` собирает локальный Maven-артефакт
`com.k2fsa.sherpa:onnx:2.0.1-nnapi2`. Нужны Linux x86_64, CMake, Python 3,
curl, Android NDK 28.2.13676358 и `ANDROID_HOME` (либо `ANDROID_NDK_HOME`).
Кэш задаётся `NEURO_NNAPI_CACHE`; по умолчанию `.gradle/nnapi`.

Исходники sherpa 2.0.1 и бинарный ONNX Runtime 1.28.2 проверяются по SHA-256.
Arm64 JNI пересобирается для Android API 27 с выравниванием ELF 16 КБ.
Это существенно: исходный sherpa AAR собран с API 21, поэтому его ветка
NNAPI исключена препроцессором. Kotlin API сохраняется без изменений.
Остальные ABI сохраняются из исходного AAR и используют CPU.
Контрольная сумма результата хранится рядом с AAR в `build-manifest.json`.

В сборке NNAPI установлен `NNAPI_FLAG_CPU_DISABLED`: эталонный CPU-драйвер
NNAPI не выдаётся за GPU/NPU. ONNX Runtime по-прежнему может выполнять
неподдерживаемые узлы на CPU. Если аппаратный драйвер отклоняет сессию или
вычисление, приложение освобождает неработающую сессию и один раз повторяет
операцию с новой CPU-сессией; в результат добавляется сообщение о fallback.
Ошибки CPU и отмена не маскируются. Патч JNI переводит исключения C++ в
Java для файловых LID/диаризации; ASR уже содержит такие обработчики upstream.

## GigaAM-v3 RNNT на Pixel 9 Pro

Драйвер `google-edgetpu` отклоняет все три графа GigaAM с исходным набором
флагов. Для энкодера GigaAM разрешена релаксация FP32 до FP16, а декодер
и joiner работают на CPU. Флаг `NNAPI_FLAG_CPU_DISABLED` остаётся активным.

На Pixel 9 Pro с Android 17 профиль распознавания записи 15,125 с содержит
162 выполнения через NNAPI в энкодере и 2129 выполнений на CPU в том же графе.
Оба режима выдали одинаковый текст. В этом прогоне создание сессии заняло
76,7 с с NNAPI и 4,9 с на CPU. Распознавание заняло 1,67 с с включённым
профилированием NNAPI и 0,72 с на CPU без профилирования. Наблюдалось
аппаратное исполнение части графа, а полное время прогона выросло.

## Обнаружение и профилирование

`OnnxAcceleration` запрашивает NNAPI только для arm64, Android 10+ и при
наличии драйвера типа GPU/ACCELERATOR. Список драйверов получен через публичный
NDK API, а не по названию процессора. Snapdragon, MediaTek и Google используют
один путь обнаружения; само наличие драйвера не доказывает выполнение модели
на ускорителе и не гарантирует ускорение.

Профилирование включается явно: `choose(..., diagnostic = true)`.
После закрытия сессий `evidence()` считает события исполнения узлов
`NnapiExecutionProvider` и `CPUExecutionProvider`. Число событий — не число
уникальных узлов. В обычном процессе трассировка выключена, поскольку ORT
накапливает события в памяти. Отсутствие профиля честно отображается как
неизмеренное распределение операций. Для очень больших трасс (>8 МиБ) нужно
анализировать JSON отдельно: интерфейс не загружает их целиком.

`acceptance.OnnxBackendProbeTest` использует подготовленные проверенные модели
Whisper tiny/диаризации и `files/validation.wav`, ничего не скачивает. Он
последовательно запускает LID, ASR и диаризацию, закрывает сессии и сохраняет
`files/onnx-backend-probe.json` с fallback, временем и фактическими профилями.
Его нельзя запускать одновременно с пользовательской расшифровкой.

Первичная проверка на подключённом Pixel 9 Pro: драйверы `google-edgetpu`
(ACCELERATOR) и `nnapi-reference` (CPU) обнаружены. Прямая загрузка настоящих
`segmentation.int8.onnx` и `tiny-encoder.int8.onnx` через ORT 1.28.2 с
`CPU_DISABLED` отклонена драйвером Google. Это основание для CPU fallback,
а не доказательство работы NPU. Полный результат Android-пробы записывается
отдельно после сборки и установки APK. Honor 200 и MediaTek требуют проверки
на соответствующих устройствах.

# Ограничение памяти аудио

WAV читается блоками; сжатый звук подаётся из каждого PCM-буфера MediaCodec
в потоковый downmix/resample. Полная копия PCM исходной частоты не хранится.
Итоговый API пока требует `FloatArray` 16 кГц, поэтому ограничение составляет
минимум из 30 минут и `Runtime.maxMemory()/16` отсчётов. При превышении
выдаётся русская ошибка с просьбой сократить запись. Блоки накопления и
итоговая копия вместе занимают не более примерно половины максимальной
Java-кучи; память нативных моделей учитывается отдельно.

Фильтр 60 Гц удаляет постоянную составляющую и низкочастотный гул без порога
тишины. Нейросетевой GTCRN использует одну потоковую сессию на запись,
сохраняет рекуррентное состояние и точную длину звука после flush. Он
обрабатывает блоки по секунде; отмена проверяется между блоками. Ни фильтр,
ни GTCRN не меняют временную шкалу исходной записи.
